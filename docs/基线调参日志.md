- **运动能力对齐（Round 0 前）**：DWB 负向 `vx`/`vy`、MPPI Omni、TEB `max_vel_y`/`acc_lim_y`

  任一项未对齐，先修配置/换 fork，不进入调参。

### 4.1 不可突破的安全与实验边界（违反即回退/停）

1. 不得超出底盘能力与任务平面合速度上限；不得改场景、实例表、裁判、共享 costmap/规划器，
   不得逐场景调参。
2. 不得碰撞；不得用危险行为换时间优势；最小间距不得低于 **0.20 m 硬底线**。
3. 不得比上一轮新增急停边沿；急停计数口径见 §6（单 run / 5 run / 20 run 分列）。
4. 工作集 25 run 必须完整（无基础设施失败）；有缺失先修套件，不得用缺失数据判停。
5. 每轮记录实际插件版本、参数 YAML 与 commit；共享配置变化必须同步三基线重跑。

> 以上边界用于判断是否**接受某轮调参改动**，不是基线成绩是否入库的筛选门。若固定预算内
> 始终碰撞/间距不达标，按规则停止调参、选最佳安全配置，并在正式 20 采集中如实记录失败；
> 不得因表现差而选择性不报或删除该基线。

### 4.2 基线优化与判停（固定预算内）

- 预算：前 5 种子、每基线最多 2 轮、三基线同预算；一轮无明显改善即停。
- **实质改善**（满足任一即可，不要求同时达到 95% / 0.30 m / 90%）：
  1. 工作集成功数增加 ≥1 run，且无新增碰撞/危险事件；
  2. 成功数不降，到达时间中位改善 ≥5%；
  3. 成功数不降，目标指标（如最小间距）改善 ≥10%，且到达时间不劣化 >10%。
- 任一场景成功数不得下降（5 run 中少 1 次即 -20pp）；若下降，除非目标指标显著改善且
  无安全事件，否则回退该参数。
- 若一轮无实质改善 → 停，保留上一轮参数；最多 2 轮。
- **95% / 最小间距 0.30 m / 急停≤1 / dynamic_stress 90% 是报告目标与 M4 参考，
  不是继续调参的强制前提**。弱基线在预算内改善后仍可定稿并如实入库，即使未达到这些目标。

**5 种子分辨率说明**：每场景工作集只有 5 run，成功率只能以 **20pp** 步进变化；
聚合 25 run 时每次成功变化约 4pp。上述判停规则是**固定预算内的工程判停**，
不是有足够分辨率的统计结论。正式 20 run 才用于 M4 对比。

**禁止**：为单个场景调专属参数；为单个指标牺牲成功率/间距；超过底盘能力上限；
把调参期 run 当正式成绩；改共享 costmap/全局规划器而不告知。

按选定 fork 的依赖与配置决定；不得把“能编译”当作“支持 omni”。

| `min_turning_radius` | 0.0（holonomic） | 固定 | 仅说明转向约束，不等于具备横移 |
| `weight_max_vel_x` | 2.0 | 跟踪慢时升 | 速度跟踪 |
| `weight_max_vel_y` | 待核实 | 仅 fork 支持时配置 | 横向速度权重 |
| `weight_max_vel_theta` | 1.0 | 转向慢时升 | 角速度跟踪 |
| `weight_acc_lim_x` | 1.0 | 一般不动 | 纵向加速度权重 |
| `weight_acc_lim_y` | 待核实 | 仅 fork 支持时配置 | 横向加速度权重 |
| `weight_acc_lim_theta` | 1.0 | 一般不动 | 角加速度权重 |
| `weight_kinematics_nh` | omni 按 fork 降低/置 0；diff 迁移 1000 | 以 fork 实测为准 | 非完整约束 |
| `weight_kinematics_forward_drive` | omni 可降/0；diff 迁移 1.0 | 倒车/横移多时调 | 前向偏好 |
| `weight_optimaltime` | 1.0 | 时间过长时升；绕行过度时降 | 时间最优 |
| `weight_obstacle` | 50.0 | 间距不足时升；窄道死锁时降 | 障碍代价 |
| `weight_dynamic_obstacle` | 10.0 | 动态场景提前绕行时升 | 仅当该 fork 真正消费动态障碍时有效；回填须注明障碍信息来源 |
| `weight_viapoint` | 1.0 | 贴线不足时升 | 路径点 |
| `weight_adapt_factor` | 2.0 | 一般不动 | 自适应权重 |
| `dt_ref` | 0.3 | 计算超时则升；精度不足则降 | 轨迹离散 |
| `dt_hysteresis` | 0.1 | 一般不动 | 离散滞回 |
| `max_samples` | 500 | 计算超时则降 | 采样上限 |
| `min_samples` | 3 | 一般不动 | 最少样本 |
| `no_inner_iterations` | 5 | 计算超时则降 | 内层迭代 |
| `no_outer_iterations` | 4 | 计算超时则降 | 外层迭代 |
| `max_global_plan_lookahead_dist` | 3.0 | 前瞻不足时升；绕行过度时降 | 全局路径窗口 |
| `feasibility_check_no_poses` | 5 | 碰撞/死锁时调 | 可行性检查 |
| `obstacle_poses_affected` | 30 | 一般不动 | 障碍影响范围 |
| `selection_dist_holonomic` | 0.8（仅 holonomic fork） | omni 主对比 | 全向选择距离 |

**Round 1 建议**：优先 `weight_obstacle` 或 `weight_optimaltime` 二选一；
计算超时再降 `max_samples`/`no_inner_iterations`。TEB 未安装/未确认前不得开跑。

**TEB 可用性验收（Round 0 前，工程侧执行、算法侧判读）**：

1. 固定 fork + commit（`costmap_converter` 按 fork 依赖决定是否启用），本机 `colcon build` 通过；
2. `controller_server` 实际加载 TEB 插件（日志出现插件类型，`ros2 param get` 可读）；
3. 发 2 m `FollowPath`，确认 `computeVelocityCommands` 被调用、`/cmd_vel` 非零；
4. omni holonomic 配置下确认 `max_vel_y`/`acc_lim_y` 生效、能输出横向 `vy`；
   若该 fork 仅非完整，立即上报，不得假定与 DWB/MPPI 同运动能力；
5. Round 0 实测平面合速度 `√(vx²+vy²) ≤ 0.6`；无限速手段则需共享执行层限速；
6. 记录插件名/版本/YAML 与动态障碍来源；任一项失败，TEB 不进入 Round 0，且不得静默删除该基线。

## 6. 指标与判停

七项指标定义见 `docs/指标定义.md`：成功率、到达时间、路径长度、平滑度、最小间距、
急停次数、动态应变。逐场景记录 1~6 项中位数/合计；`dynamic_stress` 为套件级。

**安全边界**：见 §4.1（底盘能力、无碰撞、最小间距 ≥0.20 m 硬底线、不得新增急停、
25 run 完整有效）。这些是回退/停止条件，不是“必须达到 95% 才能继续”。

**报告目标参考**（不阻断继续调参，也不阻断定稿）：成功率 ≥95%、最小间距中位 ≥0.30 m、
急停 ≤1、动态场景 `dynamic_stress` ≥90%。未达到时如实记录，最终仍可在预算内定稿入库；
M4 判定的正式数字来自 20 run 采集，不用调参工作集替代。

**急停计数口径**：

- 单 run：`/safety/stop` 上升沿计 1 次；
- 调参工作集：分别记录每场景 5 run 合计与全部 25 run 合计；
- 正式 M4：每场景 20 run 合计（`docs/指标定义.md`），阈值 ≤1 指该口径；
- 安全边界：不得比上一轮新增急停边沿，不以“合计 ≤1”作为继续调参的强制前提。

**定稿选择**：在固定预算与安全边界内，选综合表现最好的参数（成功率 → 到达时间 →
最小间距 → 平滑度）；不以单项最优、也不以未达到报告目标为由提前淘汰基线。
若 2 轮后仍不达标，保留最佳安全参数并记录缺口，交工程组按正式 20 入库。

**9-3 时限冻结（正式 20 采集前）**：定稿参数后，用定稿工作集（或单独 5 种子计时）计算
每个场景、每个基线的**成功 run 到达时间中位数** `t̃(s,j)`，然后冻结：

```text
T_s = max( T_min,s , 1.5 * max_j t̃(s,j) )
T_min = 60 s（mixed 75 s）
```

- 只统计**成功 run**；超时/未到达不得当成功到达时间参与中位数。
- 若某基线在该场景无成功 run：记录缺失并排除出 `max_j`；若三基线都无成功 run，
  **保留预定 `T_min`（60 s；mixed 75 s）作为临时值，并上报双方确认最终时限**；
  不得事后根据 MPC 成绩或“最有利”结果挑时限。
- `T_s` 对 MPC 与三基线完全相同；使用同一实例表、同一裁判规则。
- 必须在正式 20 采集**开始前**冻结；若采集后必须改，停止采集、重算并重跑全部受影响
  官方成绩，不能新旧混用。

**5 种子与正式 20 的分工**：工作集只用于调参判停（接受 20pp 分辨率限制）；
正式 20 run 才用于 M4 对比与报告，不把工作集成绩混入入库。

## 10. 待确认决定

1. **主对比运动学**：保持 **omni**（原方案）；diff 仅迁移冒烟。若 TEB 实测无法 omni，
   双方另议（换 fork/换基线/另设 diff 辅助比较），不单方面改主实验，也不静默删除 TEB。
2. **任务平面合速度 0.6 m/s**：约束 `√(vx²+vy²) ≤ 0.6`；与 W4 MPC 对齐；工程侧现有基线
   若用其他口径，先统一再开跑。
3. **TEB 可用性**：源码 fork/commit/插件名；必须通过 §5.3 六项实际验证，含 `max_vel_y`/
   `acc_lim_y` 是否真正支持。不可用则 9-2 无法凑齐三基线，需上报，不能默认可用或擅自删除。
4. **共享 costmap/规划器**：确认三基线同配置；若 M2 已有差异，先统一。
5. **DWA 即 DWB**：Nav2 的 `dwb_core::DWBLocalPlanner` 作为 DWA 基线；报告须准确注明
   “DWA 基线由 Nav2 DWB 实现”，不写成独立 DWA 实现。
6. **9-3 时限冻结**：必须在正式 20 采集前完成；采集开始后改时限则全部受影响成绩重跑。
7. **平面限速执行层**：确认三基线通过原生或共享执行层满足合速度 ≤0.6，不能只在 YAML
   分别限制 vx/vy。
8. **9-3 聚合口径**：每场景取三基线成功 run 中位到达时间的最大值 ×1.5，再取下限；
   缺失数据按 §6 规则处理，需双方冻结。
