# 9-3 行人作为"静态地图中的动态障碍"：实现、证据与影响面

> 适用范围：工程侧（9-3 执行）。改动只涉及**执行层/场景信息注入**与一个 Nav2 调参项，
> 不改契约、不改判分口径、不改 9-1 §6 的时限公式。
> 三个基线（DWA / MPPI / TEB）拿到的是**同一份**行人信息，公平性不破坏。

## 1. 目标与设计口径

行人原本只存在于 Isaac 场景里（有碰撞几何、能被雷达看到），但底盘三个基线**都没有
轨迹预测**：行人横穿时机是按"机器人按 0.6 m/s 直线走"反解出来的（契约 `t_meet`），
所以 DWA/MPPI/TEB 只会在"人已经到跟前"时才反应，300 次正式成绩里 65 次失败全部是
`collision`，且全部落在 `dynamic_pedestrian` / `mixed`。

本方案把行人做成**地图里的动态障碍**：驾驶层不再依赖"现测"，而是从地图里读到
"行人现在在哪、接下来 4 s 会扫过哪块地"，于是可以在**横穿线之前**就决定停车礼让。

口径：

| 项 | 取值 | 理由 |
|---|---|---|
| 信息来源 | 契约 `instances.yaml` 的行人参数（`x_cross/speed/t_meet/dir/r`） | 契约公式就是匀速直线，未来可精确推算；不引入"上帝视角的额外能力"，因为它等价于"感知+预测 4 s" |
| 注入通道 | `nav_msgs/OccupancyGridUpdate` → `/map_updates` → 代价地图 `static_layer` | Nav2 原生机制，三个基线都走同一张代价地图 |
| 生效范围 | 全局 + 局部代价地图 | 全局决定规划，局部决定控制；实测只有局部的补丁真正生效（§3.2） |
| 障碍形状 | **横穿走廊**（矩形），不是圆盘 | 圆盘会让机器人贴着横穿线停车，行人直接穿过去（§4.1） |
| 预测时域 | 4.0 s | A/B 证据见 §4.2 |
| 控制器耐心 | `failure_tolerance` 0.5 s → 10 s | 礼让会产生 4~5 s 的"当前无可行轨迹"，0.5 s 就中止会把成功记成失败（§4.3） |

## 2. 实现（4 个改动点）

### 2.1 `/map_updates` 的消息类型（根因，之前整个功能是死的）

`nav2_costmap_2d::StaticLayer` 在 `subscribe_to_updates: true` 时订阅的是
**`map_msgs/msg/OccupancyGridUpdate`**，不是 `nav_msgs/msg/OccupancyGrid`：

```
$ ros2 topic info /map_updates -v
Type: map_msgs/msg/OccupancyGridUpdate
Subscription count: 2      # /global_costmap 与 /local_costmap 各一个
  Reliability: BEST_EFFORT   Durability: VOLATILE
```

之前按 `nav_msgs/OccupancyGrid` 发布，DDS 因类型不匹配**根本不投递**。证据是三次 run
的成绩在小数第 4 位完全一致（`-0.2979` / `-0.2978`、`-0.2973` / `-0.2970`）——等于
"加了这个功能"和"没加"完全一样。改成 `OccupancyGridUpdate`（`x,y,width,height` 用
**原始地图栅格的绝对格坐标**，`data` 逐格 0/100）后，补丁才真正进代价地图。

### 2.2 补丁必须由 `/odom` 回调驱动，不能用 timer

跟随阶段驱动节点在 `rclpy.spin_once` 里按节拍跑，`create_timer` 会被饿死：实测
`/map_updates` 一直停在 `t=0` 的静态位置（探针看到 625 个致命格卡在行人初始位置
`x≈3.65, y∈[6.43,7.33]`）。改为在 `odom_cb` 里按 ≥0.2 s 的最小间隔触发。

### 2.3 横穿走廊模型（核心）

每个行人本拍占用一个 **path frame 轴对齐矩形**：

```
x ∈ [x_cross − W, x_cross + W]        # W = 0.343 + 0.30 + 0.10 = 0.74 m
y ∈ [min(y_now, y_pred) − r, max(·) + r]
y_now  = dir·speed·(tp − t_meet)      # 契约公式
y_pred = dir·speed·(tp + 4.0 − t_meet)
```

- `0.343` = 底盘八边形外接半径，`0.30` = 行人与底盘判定用的圆半径，`0.10` = 余量。
  法向半宽必须覆盖这两者之和，否则机器人会认为自己"站得够边上"。
- 每拍补丁只重绘 `上一拍走廊 ∪ 本拍走廊`，矩形内其它格子一律回填**静态地图真值**，
  所以不会误擦墙、也不会留下"幽灵障碍"。
- 行人走过去以后矩形自然不再覆盖车道（只覆盖"当前 → 未来"），机器人及时解封。

### 2.4 `failure_tolerance` 0.5 s → 10 s

`controller_server` 的耐心：连续"无可行轨迹"超过该值就中止 FollowPath。礼让时
DWA 每拍都输出 `No valid trajectories out of 6656!`，0.5 s 就触发
`Controller patience exceeded` → 本来"等一下就能过"的 run 被记 `failure_class=other`。
一次性礼让约 4.8 s，取 10 s（仍远小于 60/75 s 时限；真卡死由 `progress_checker` 兜底）。

同时把三份 baseline YAML 里重复的 `failure_tolerance` 删掉（多控制器同栈时这是
server 级参数，只能有一份；`_merge_controllers()` 有一致性校验）。

## 3. 证据

### 3.1 探针（`/tmp/probe2.py`，seed 203，DWA）

```
tp= 5.87 | robot=(3.25,-0.00,v=0.60) | ped(3.65,2.11) d=2.15 gv=0 lv=100 | L_lethal=2571
tp= 6.80 | robot=(3.59,-0.00,v=0.00) | ped(3.65,1.33) d=1.33 gv=0 lv=100 | L_lethal=3161
tp= 8.27 | robot=(3.59,-0.00,v=0.00) | ped(3.65,0.09) d=0.11 gv=0 lv=100 | L_lethal=3161
tp= 8.75 | robot=(3.59,-0.00,v=0.00) | ped(3.65,-0.31) d=0.32 gv=0 lv=99  | L_lethal=3161
tp= 9.72 | robot=(3.59,-0.00,v=0.00) | ped(3.65,-1.12) d=1.13 gv=0 lv=0   | L_lethal=3161
```

- `lv=100` 出现在行人**契约真值位置**上 → 局部代价地图的补丁位置正确。
- `gv=0` → 全局代价地图**没有**拿到补丁（原因未定位，见 §5 待办；当前不影响结论）。
- 机器人在 `x=3.59`、行人横穿线在 `x=3.65`：只差 0.06 m。行人照着直线走过去，
  直接穿过机器人（`d=0.11 m`）。这就是"圆盘模型"失败的原因。

### 4.3 `mixed` 剩下的问题

- `dwa` seed 502/503 仍 `other`：混合场景里静态障碍把道路压窄，走廊 + 静态障碍
  同时压上来时 DWA 找不到可行轨迹（日志 `No valid trajectories`），30 s 耐心也熬不住。
- `dwa` 505 / `teb` 505 仍撞（−0.117 / −0.037）：机器人绕过走廊"前头"时
  间距只剩 0.04 m 级别，说明端头余量在窄道 + 有静态障碍的布局下还不够。
- 结论：动态行人这一侧的机制在**空旷横穿**（`dynamic_pedestrian`）已经可靠；

## 5. 影响面与待办

1. **参数冻结被打破**：`dwa.yaml/mppi.yaml/teb.yaml/mpc.yaml` 与
   `nav2_baseline.launch.py` 都变了，`results/9-1参数定稿.md` 里的 sha256
   需要重新登记；正式 300 run 若要重跑，应在新冻结版本上重跑（至少动态两个场景）。
2. **9-3 时限**：`T_s` 只取成功 run 的 `max_j t̃`，礼让会拉长成功 run 的时间。本场景
   成功 run 实测 19~23 s，`1.5×` 后仍 < 60 s 地板 → `T_s` 不变，需在正式重跑后复核。
3. **全局代价地图收不到补丁**：`ros2 topic info` 显示 `/global_costmap` 确实订阅了
   `/map_updates`（`map_msgs/OccupancyGridUpdate`，BEST_EFFORT），探针却看到行人处恒为 0，
   而局部代价地图有 100。当前"全局走直线 + 局部礼让"的组合是稳定的（也没有 `replans`
   抖动），所以不做进一步处理；但要记一笔，避免以后误判成"全局也吃到了预测"。
   下一步可做的判定实验：发一个**只有预测位置**（行人当前不在那里）的 patch，
   看哪个代价地图出现致命格——局部出现即证明补丁生效、全局不出现即证明被 `static_layer`
   的 `process()` 覆盖（或滚动窗口索引问题）。
4. **MPC**：本方案只改变代价地图内容，MPC 接入后同样能吃到这份信息（它订阅同一张
   代价地图），无需额外接口。

## 6. 2026-11-17 修掉的真 bug：行人 prim 从来没绑上（"Isaac 里看不到行人移动"）

**现象**：终端里 `[SIM] 行人 t_rel=…` 的坐标在变，但 Isaac 视口里的行人纹丝不动。

**根因**：`isaac_sim_bridge.py` 里行人 prim 是**写死路径**取的：

```python
stage.GetPrimAtPath("/World/ScenarioFrame/Pedestrian_%02d" % i)   # 永远 invalid
```

而 `scenes.py` 生成本文时 `ScenarioFrame` 这个 Xform 在把子级写下去之前就关闭了
（缩进只影响观感、不影响 USD 层级），所以行人的真实路径是 `/World/Pedestrian_00`、
`/World/Pedestrian_01`（障碍物、地面同理，都在 `/World` 下，`ScenarioFrame` 是个空壳）。
`GetPrimAtPath` 拿到 invalid 后只打一行
`[SIM] 警告：场景里没有 Pedestrian_XX 的 prim（行人 XX 无法动画）`，
于是**只有终端里的契约数学在变，USD 里的位姿一直是 t=0**。

**修复**：改成按 prim 名字在整棵 stage 里查（`stage.Traverse()` 里匹配 `Pedestrian_*`），
把实际路径打出来；另加一行 `[SIM] USD 位姿: …` 每 2 s 打印**从 USD 读回来**的 translate，
以后再有类似问题，看这行就知道位姿到底有没有写进去。

修复后实测（mixed seed 504，GUI 模式）：

```
[SIM] 行人 prim 绑定：Pedestrian_00 → /World/Pedestrian_00
[SIM] USD 位姿: Pedestrian_00=[7.54, -5.47, 0.85]      ← 锚点前，停在 t=0
[SIM] 收到 /sim/episode_start：行人相位锚点 t=85.37 s
[SIM] USD 位姿: Pedestrian_00=[7.54, -3.02, 0.85]      ← 位姿真的在推进
[SIM] USD 位姿: Pedestrian_00=[7.54, -0.60, 0.85]
```

**影响面（必须记住）**：

1. **已跑的 300 run（`out/9-2_official_v2`）里，行人一直停在 t=0 位姿**（离道路中心 5~6 m，
   看着就是两个红色圆柱）。这不影响成绩有效性——判分的行人间距是**按契约公式**算的
   （`judge.py` 的 `pedestrian_xy`），不看 Isaac 里的几何；但它说明"机器人是靠注入的
   横穿走廊在避让"，而不是靠雷达看到人。
2. **雷达看不到行人**：`omni.physx` 的 `raycast_all` 能打到 `Obstacle_*`（2~3 个点/个），
   但打不到行人圆柱（试过给行人加 `PhysicsRigidBodyAPI` + `kinematicEnabled`，
   仍然为 0 命中，原因未定）。也就是说行人现在**只是可视化 + 代价地图里的走廊**。
   下一步如果要"真感知"这条路，需要把行人做成真正会动的刚体并确认 raycast 命中，
   然后**重跑 300 run**（成绩会变）。
3. `instances.yaml` / 判分口径 / `T_s` 都不需要改（都不依赖 Isaac 侧几何）；
   `run_workset.py` 也不变。改的只有 `isaac_sim_bridge.py`（不在冻结哈希表里）。

## 7. 2026-11-17 复核：`/map_updates` 补丁通道其实是**死的**（重要更正）

修好行人 prim 绑定（§6）后复测 mixed seed 504，DWA/MPPI 卡在行人横穿线前不动。顺着查下去，
发现两件事：

### 7.1 Nav2 的 `static_layer` 补丁通道在本环境无效

隔离实验（栈里只有 Nav2，手工发补丁）：

| 实验 | 结果 |
|---|---|
| 按 `map_msgs/OccupancyGridUpdate` 发、QoS 与订阅端一致（BEST_EFFORT/VOLATILE） | 局部代价地图目标格**仍是 0** |
| 同一区域改写 0（擦除） | 无变化 |
| 换成 RELIABLE 发 | 无变化 |
| 全局代价地图同样检查 | 无变化 |
| `ros2 topic info /map_updates -v` | 两个订阅者都在、类型对、QoS 对 |

即：**§2.1~§2.3 描述的那条注入通道从来没生效过**。300 run（v2）里
`dynamic_pedestrian` 从 40% 涨到 75~100%、行人碰撞从 65 降到 3，**不是走廊注入的功劳**，
而是两个 server 级参数的功劳（`failure_tolerance` 0.5→10 s、`movement_time_allowance` 10→30 s：
控制器不再"一有短暂无可行轨迹就中止"，robots 得以在原地等，等的过程恰好把行人让过去了）。
这一点必须写清楚，否则会误判我们的机制在起作用。

### 7.2 顺带查清 mixed 卡死的真因

### 7.6 Bug 已修：`declare_parameter` 在 costmap 层里会让 controller_server 停摆

**定位过程**（同场景 mixed seed 504、局部代价地图用 stage 逐级开关、一次编译）：

| stage | 层做什么 | 结果 |
|---|---|---|
| 0 | 什么都不做 | 机器人正常跑（最远 x=6.65） |
| 1 | **只加 `declare_parameter` 三次** | **机器人一动不动（最远 x=0.00，75 s 超时）** |
| 2 | + 订阅（建在 costmap 节点上） | 一样不动（被 stage 1 掩盖） |
| 4 | 完整逻辑、**不 declare 参数**、订阅改由自带独立节点 + 独立执行器线程 | **机器人正常跑**（`最大|vx|=0.266 位移=(6.20,0.92)`） |

`gdb` 抓栈看到控制线程停在 `nav2_controller::ControllerServer::computeControl()` 的
`rclcpp::Context::sleep_for`（正常控制节拍）；debug 日志停在
`Path end point is (11.93, -0.02)` 之后再无输出——即 computeControl 在循环但不产速度。
结论：**在 `Layer::onInitialize()` 里对 costmap 生命周期节点调用 `declare_parameter`
会破坏 controller_server 的控制循环**（机理未深究，规避即可）。

**规避做法（已落地）**：

1. 层里**不调用 `declare_parameter`**，参数改从环境变量读（`PED_LAYER_TOPIC` / `PED_LAYER_THRESHOLD`）；
2. 订阅**不建在 costmap 节点上**，改为层自带 `rclcpp::Node` + `SingleThreadedExecutor` 独立线程；
3. 恢复逻辑两处修正：
   - 按**世界坐标**恢复（滚动窗口原点每拍都在变，存栅格索引会指到别的格子）；
   - 恢复时把 `LETHAL/INSCRIBED` 一律还原成 `FREE_SPACE`（否则会把上一拍 inflation 写下的
     inscribed 环带永久还原回去）；
4. 层放在 `inflation_layer` **之后**，并**自己写 0.25 m 的 inscribed 环**（inflation 层只加不减，
   靠它给走廊膨胀必留永久环带）。实测 costmap 快照里只剩"当前走廊 + 它自己的环"，无累积。

**仍然存在（与本修复无关）**：整条 episode 跑下来机器人还是停在 `x≈6.6`（行人横穿线前）。
同样的停滞在"局部挂一个**完全空**的层"和"冻结配置"下都能复现 → 它来自"行人现在真的会动、
而代价地图上行人历史位置的格子擦不干净"，属于另一条线（点云层清图），不是走廊层的问题。

**当前配置状态**：局部代价地图已挂 `ped_corridor_layer`（`inflation_layer` 之后），
采集器改为向 `/ped/corridor` 发走廊栅格。`nav2_common.yaml` 与 `nav2_driver.py` 的 sha256
因此与 9-2 正式成绩的冻结值不同 —— 若要出正式成绩需按新配置重跑。

## 8. 2026-11-17 "行人走后机器人停滞"：已解决（mixed 三个基线跑通）

### 8.1 停滞的真因（三条，逐条都实测过）

1. **局部点云层把行人标进去以后永远不回收。** 行人现在是仿真里真正会动的圆柱，
   点云层标上后，走过的那条带一直是 lethal；`voxel_decay: 2.0` 也不管用；
   inflation 再给它套一圈 inscribed。实测混合场景横穿车道 `(7.5, 0)` 的代价从 20 s 起
   一直是 99 不回落，机器人停在 `x≈6.6` 等到 `progress_checker` 判失败。
   **处置**：局部点云层 `marking: false`（本实验口径是"障碍位置已知"：静态障碍来自
   `static_layer`，行人来自走廊注入，都不依赖点云；`clearing` 保留做兜底）。
2. **我那个走廊层的恢复逻辑把 inflation 的值当原始代价还原。** 恢复时若 `old_cost` 是
   `LETHAL/INSCRIBED`，会把它原样写回去 → 膨胀环带永久残留。
   **处置**：这两类一律还原成 `FREE_SPACE`。
3. **没有走廊时采集器不发补丁** → 层一直持有上一帧的走廊栅格，每拍把早该放行的栏杆
   重新写回去（实测 seed 501：两个行人都已走远，代价地图里还是 lethal，机器人最后硬撞）。
   **处置**：没有走廊时也发一个 1×1 的空补丁，让层把上一拍清空。

### 8.2 走廊模型最终形态：道口栏杆（level-crossing gate）

不再画"行人当前位置→未来 7 s"的长条，而是：

```
行人只要"已在马路窗口内（|y| ≤ 4.2 m）"或"3 s 内会进入"，
就在 x_cross 处把**整条路宽**封住（x ∈ [x_cross±0.74]）；
行人离开窗口后立刻抬杆放行。
```

理由：长条模型下机器人会从栏杆"前头"绕过去（穿透 −0.30），或者被走廊"吞进去"
（停在 x=5.32 与行人重合，随后被判碰撞）。道口栏杆只有一个后果——停在栏杆外侧
（`x_cross − 1.08 m`）等，杆抬起再走。

## 10. 为什么 runs 1/2（seed 501/502）会撞人（corridor 口径）

### 10.1 测到的事实

用 `out/mixed_fix/`（corridor 口径）的轨迹 + `instances.yaml` 逐条算出来的：

| seed | 两条横穿线 x | 两线间距 | 机器人到第一条线前 1.1 m 的时刻 | 行人 t_meet | 全程低速(<0.1 m/s)时间 | 判定 |
|---|---|---|---|---|---|---|
| **501** | 4.25 / 5.25 | **1.0 m** | 6.1 s | 8.5 / 10.0 s | 3.7 s | collision −0.30 |
| **502** | 6.03 / 7.66 | **1.6 m** | 8.7 s | 10.2 / 10.9 s | 32.5 s | collision −0.30 |
| 503 | 3.97 / 7.18 | 3.2 m | 6.0 s | 9.1 / 10.3 s | 0.7 s | OK |
| 504 | 7.53 / 7.53 | ≈0（同一位置） | 11.6 s | 8.6 / 9.0 s | 0.8 s | OK |
| 505 | 6.94 / 3.94 | 3.0 m | — | 8.0 / 11.0 s | — | OK |

撞人时刻（501，用轨迹 + 契约公式算）：**t_rel = 11.58 s，机器人 (5.30, −1.07)，行人 (5.25, −1.06)**
—— 两者在横穿线上完全重合，穿透 0.30 m。也就是说：机器人正横穿到一半，行人正好走到同一点。

另一个关键差异：**501/502 的两条横穿线几乎挨在一起（1.0 / 1.6 m）**，两条"道口栏杆"在 x
方向上拼成一条 2.5~3.1 m 宽的连续带；而 503/505 的两条线相距 3~3.2 m，中间留得下通道；
504 的两条线在同一位置（x=7.53），等价于一条栏杆。501/502 是唯一"两条线很近但又不是同一条"的
两种情况，这正是它们跟其它三个种子的结构性差别。

### 10.2 机制（已确认 + 待确认）

- 已确认：撞人不是"没让开"，而是**机器人横穿到一半时行人到达同一点**，且此时
  `|y_ped| = 1.06 m ≤ 4.2 m`，按道口栏杆规则那条栏杆**应当处于关闭状态**。
- 已确认：两条栏杆拼成 2.5~3.1 m 连续带后，机器人需要"一次穿过两条栏杆"，
  而它到达栏杆前的时刻（6.1 / 8.7 s）**早于行人到达横穿线的时刻**（8.5~10.9 s），
  留给它的判断余量只有 `PED_GATE_ETA_S = 3 s`。
- 待确认：机器人为什么最终还是进了栏杆带（按几何它应该在 x_cross−1.08 m 停住）。
  需要一次带层内日志的运行（记录每拍写入多少格、栅格 bbox），确认是
  "栏杆没写进代价地图" 还是 "写进去了但 DWA 从缝里挤过去"。

### 10.3 拟采取的修法（按优先级）

1. **合并近距离栏杆**：两条横穿线间距 < 2 m 时视为一个道口，用 `[min(x_cross)-0.74, max(x_cross)+0.74]`
   的整条带宽，并且**两条行人全部离开窗口**才抬杆（现在每条栏杆各自独立开合，容易出现
   "第一条抬了、第二条还没落"的缝）。
2. **提前量从 3 s 提到 6 s**（`PED_GATE_ETA_S`）：机器人从"到达栏杆前"到"穿过整条带"大约需要
   3.5~4.5 s，3 s 的提前量不足以让它安心进带。
3. 层内日志确认写入格数（见 10.2 待确认项）。

  `Received a goal, begin computing control effort.` 与 `Selected goal checker`；
- 之后 `/cmd_vel_raw` **一条消息都没有**（用 `scripts/dev_probe_cmd.py` 抓三级链路：
  `raw[0]`，而 `lim`/`cmd` 只是限速器按 19 Hz 发 0）；
- 机器人 75 s 停在原地，`peak_planar_speed_mps = 0.0`、`path_length_m = 0.0`；
- 控制器**没有任何 WARN/ERROR 日志**，开 `log_level:=debug` 也一样安静；
- 但局部代价地图的更新循环是活的（层内 `updateCosts #N` 稳定 8~10 Hz 递增）。

### 11.2 定位过程（可复现）

1. `gdb -p <controller_server> -batch -ex "thread apply all bt"`：
   唯一的控制线程停在 `rclcpp::Context::sleep_for` ← `ControllerServer::computeControl()`。
2. 在该状态下用 gdb 打 `computeAndPublishVelocity()` / `isGoalReached()` 断点，
   **45 s 内一次都没命中** → 循环体根本没进，每一拍都在 sleep 前被守卫挡掉。
3. 反汇编 `libcontroller_server_core.so` 的 `computeControl()`，守卫看得很清楚：

   ```asm
   call nav2_costmap_2d::LayeredCostmap::isCurrent()
   test %al,%al
   jne  <compute>            ; 为真才往下算
   ...  sleep 10 ms; 重试     ; 为假就一直等
   ```

### 11.3 根因

`LayeredCostmap::isCurrent()` = **所有 layer 的 `Layer::isCurrent()` 逻辑与**，
而 `Layer::isCurrent()` 直接返回基类成员 `current_`（默认 false）。
Nav2 自带层都在 `updateBounds()`/`updateCosts()` 里把它置真，**自研层从来没置过**，
于是 `isCurrent()` 恒为 false，控制器永远等在那里：

> 收到 follow_path 之后不产速度、不打印日志、也不报错——完全静默。

这条解释了 §7.5/§7.6 里所有"层一启用机器人就停"的现象，之前归因给
`declare_parameter`/更新窗口扩张都是错的（那两个改动本身无害，只是不解决问题）。

### 11.4 修法

在 `ped_corridor_layer.cpp` 里：

- `updateBounds()` 首行 `current_ = true;`
- `updateCosts()` 入口（早退之前）也 `current_ = true;`
- `onInitialize()` 里显式 `current_ = false;`，等第一拍更新再置真。

`updateBounds()` 保持**不扩张**更新窗口（滚动窗口本来就写不进 7 m 外的格子）。

### 11.5 结果（修复后，mixed_04 / DWA 单例）

```
mixed  run=4  mixed_04  success=True  到达=30.38 s  间距=0.117  急停=0
```

层内日志同时出现了真正的写入：

```
[ped_corridor] 写入 3612 格；栅格 33x200 原点(6.70,-5.00) 收到消息 93 条
```

即：机器人走到道口前，栏杆带（1.65 m × 10 m）确实被写进了局部代价地图。

### 11.6 紧接着的第二轮修复：纯栏杆带 + 机器人安全岛

`current_` 修好之后，mixed（5 种子 × 3 基线）从 0/15 变成 **11/15**
（mppi 5/5；dwa 3/5：seed 502 卡死、503 未到达；teb 3/5：seed 501/503 撞人）。
层的日志暴露出两个结构性问题：

1. **`/ped/corridor` 沿用了 `/map_updates` 的"重绘补丁"语义**：补丁里除了栏杆带，
   还把**静态地图占用格**和**每个行人 0.4 m 圆盘**一起标成 100，补丁 bbox 又随行人
   走到 |y|>20 m 而膨胀（实测出现 `52x800`、原点 y 从 −20 漂到 −5 的补丁）。
   消费端把这些 100 一律写成 LETHAL、下一拍又把"上一拍写过的格子"恢复成 FREE，
   于是**静态墙在 FREE/LETHAL 之间来回抖**，代价地图自相矛盾
   （mixed seed 502：机器人卡在 x=7.4 达 25 s，`failure_class=other`）。
2. **栏杆会把自己罩住**：机器人一旦进入栏杆带，带内的 LETHAL 让 DWA 的每条轨迹都判撞，
   机器人再也出不来。

对应改法：

- **驱动侧**：`/ped/corridor` 只发栏杆带本身（`rects` 内 100、其余 0），
  不再回显静态地图、不再发行人圆盘；bbox 只取"本拍栏杆 ∪ 上一拍栏杆"。
  行人"身体"由雷达口径负责，走廊口径只表达"道口栏杆"这个抽象。
- **层侧**：恢复逻辑不再回写 `old_cost`（它可能是静态墙的 LETHAL），
  改为"当前值是 LETHAL/INSCRIBED → 还原成 FREE"，其余一律不动；
  写栏杆时跳过**机器人中心 0.85 m 以内**的格子（安全岛），保证机器人永远有可行动作。

### 11.7 第三轮：判分线与控制器内部公差的差值、以及"等杆"的耐心

`current_` + 纯栏杆带修好后，mixed（5 种子 × 3 基线）到 **14/15**。剩下三类失败逐条查清：

1. **案例：`follow_path` 返回 SUCCEEDED，评测却判"未到达"**
   （mixed seed 503 / DWA：目标 11.342 m，停在 11.095 → 差 **0.258 m**，`follow_result=4`）。
   机制：controller_server 用 **TF 位姿** 判到位，评测用 **里程计位姿**，两者差几厘米，
   判据都是 0.25 m 时刚好骑在线上。→ 契约不变，把**控制器内部**的目标公差收紧到
   `xy 0.18 / yaw 0.15`（`SHARED_CONTROLLER_PARAMS` 与四个 `baselines/*.yaml` 必须同时改，
   否则 launch 的"多控制器同栈参数唯一性"检查会直接报错退出）。
2. **案例：`Controller patience exceeded` / `Failed to make progress`**
   （mixed seed 501 / TEB 等：停在合并后的栏杆带里 21 s）。
   机制：礼让行人要**停车等杆**，一次封杆最长约 20 s（两个行人前后横穿），
   而 `failure_tolerance` 只有 10 s。→ 放宽到 **30 s**（仍由 `movement_time_allowance`
   与场景时限 60/75 s 兜底）。
3. **案例：mixed seed 502 / DWA 停在 (7.40, 0.22)**。
   实测证据：该时刻栏杆已抬（`/ped/corridor` 已发空补丁），层日志显示
   `master 内 LETHAL=1045`（只剩静态障碍，栏杆带为 0），控制器从此刻起
   `/cmd_vel_raw` 基本不再发布，30 s 后 `Failed to make progress`。
   seed 502 在 x≈8.2~8.9 有 **三个障碍物挤在一起**（r=0.52/0.51/0.36），
   另有 (7.29,−0.64) r=0.33，机器人被夹在缝里；契约不允许倒车，DWA 卡在局部极小。
   **这不是栏杆造成的**：历史上 DWA/502 在四种口径下都是 7.45~7.47 m 处失败
   （`mixed_fix`/`mixed_gate` 撞人、`mixed_gate_cur`/`mixed_v2` 过不去），
   MPPI/TEB 同一场景能过。列为 DWA 基线在该种子上的已知局限。

### 11.10 复盘：这个 bug 为什么藏了这么久

1. **失效是静默的**。`current_` 没置真 → Nav2 控制器在 `isCurrent()` 上空转，
   没有日志、没有错误码、`/cmd_vel_raw` 一条不发；只有"机器人不动 + 峰值速度 0"这一条线索。
2. **层内日志缺失**。最初只在 `updateCosts` 入口打印 `enabled=`，没打印"写了几格"与
   "master 里回读到几格 LETHAL"，于是无法区分"没写进去"和"写进去了但控制器不采信"。
3. **假归因**。`declare_parameter`、`updateBounds` 扩张窗口都"看起来"能解释冻结，
   逐级 stage 对照还把 `enabled_=false` 掩盖掉了——真正的判据只有一条：
   **反汇编/断点确认控制器卡在哪个判断上**（§11.2）。
4. 教训：给 Nav2 写自定义 costmap 层时，`current_`、`enabled_`、`isClearable()`、
   `matchSize()` 这些"框架约定"必须显式处理；调试时先确认框架侧的等待条件，
   再怀疑自己的几何/算法。

### 11.11 第四轮：`0.85 m` 安全岛改成"只留身后退路"（v3）

看完 v2 的逐例轨迹发现问题：**对称的"安全岛"等于给机器人开了一条推土机通道**——
每一拍它都能把正前方 0.85 m 内的栏杆擦干净，于是它一点点拱进落着的栏杆带
（mixed_01/DWA 实测：x 从 3.19 蹭到 4.69 用了 13 s，与行人只剩 0.10 m 间距）。

两处改动：

1. **层**：对称安全岛 → **身后退路**。只跳过"机器人身后 1.2 m 且投影在后方"的格子，
   正前方与两侧照常落杆。效果是"进不去、退得出"：机器人被罩住时能倒出来，
   但绝不可能穿过栏杆带穿过道口。
2. **驱动**：**栏杆不落在机器人身上**。若机器人的 path 系 x 已经落在某条合并栏杆带
   `±0.15 m` 内，这一拍就不落这条杆（已经进场就别再关门）。
   否则它被 LETHAL 包住，DWA/TEB 每条轨迹都判撞，只能等 `patience` 中止。

- 唯一失败仍是 **DWA/502**（障碍簇局部极小，§11.7-3，历史各版本同点位失败）。
