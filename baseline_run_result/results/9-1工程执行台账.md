## H. 安全层与动态行人（2026-11-14，补 §G.4 的第 3、4 项）

### H.1 速度通路改成三级（职责分开，写清楚免得互相背锅）

```
controller_server ─/cmd_vel_raw─▶ flat_speed_limiter ─/cmd_vel_limited─▶
    safety_supervisor ─/cmd_vel─▶ Isaac 桥接（底盘只订阅 /cmd_vel）
```

| 层 | 管什么 | 不管什么 |
|---|---|---|
| `flat_speed_limiter` | 契约口径的形状：`√(vx²+vy²)≤0.6`、`|wz|≤1.5`、加速度限幅；纯几何、四控制器同等生效 | 不判安全事件 |
| `safety_supervisor` | 安全事件：人工接管 `/safety/stop_request`、`/odom` 超时（0.5 s）、碰撞临近（机体系 0.36 m 内有障碍点） | 不改控制器的正常输出；越限只缩回、不判急停 |

`/safety/stop`（Bool）只有在**真的要制动**时才为真，9-1 的 `estop_count` 数它的上升沿。
`speed_invariant`（上游越限）刻意**不算**急停：实测 0.6 m/s 边界上每分钟抖动 20~30 次，
计进去会让 estop 全是噪声，真正该被看到的"操作员接管/碰撞临近"就被淹没了（这一条是
第一版实现踩出来的，记在这里免得以后又改回去）。

自测：`python3 scripts/safety_supervisor.py --selftest` → 8 项全 PASS；
`flat_speed_limiter.py --selftest` → 6 项全 PASS。

### H.2 动态行人按契约公式推进

* `scenes.py` 把行人的契约参数（`x_cross / speed / t_meet / dir / r`）以 JSON 写进 USD 的
  `customLayerData.pedestrians_json`；
* `isaac_sim_bridge.py` 每帧按 `y = dir·speed·(t − t_meet)`、`x = x_cross` 更新
  `/World/ScenarioFrame/Pedestrian_XX` 的 translate（匀速直线、无停住、无钳位，与契约一致）；
* **相位锚点**：`/sim/episode_start` 把本 run 的 `t=0` 传给仿真侧。这一步不能省——预热
  要 20~40 s，行人若按 Isaac 累计时间推进，等真正开跑时相位早已跑掉。实测锚点生效后
  `t_rel=8.93 s → y=0.10 m`、`t_rel=10.93 s → y=1.64 m`，与公式 `(t−8.798)×0.768` 完全吻合；

## J. TEB abort 的真实原因（2026-11-14 结案）与四控制器同表验证

### J.1 根因：`goal_checker` 名字不存在

开 `controller_server` 的 debug 日志（新增 launch 参数 `log_level:=debug`，从
`simulation.launch.py` 透传到 `nav2_baseline.launch.py`）后，一条就定位：

```
[ERROR] [controller_server]: FollowPath called with goal_checker name general_goal_checker
        in parameter 'current_goal_checker', which does not exist.
[WARN]  [controller_server]: [follow_path] [ActionServer] Aborting handle.
```

**根因**：`teb.yaml` 只写了 `controller_plugins` 和 `FollowPath`，漏了
`goal_checker_plugins: ["general_goal_checker"]` 与 `general_goal_checker` 段。
采集器发 `follow_path` 时固定带 `goal_checker_id="general_goal_checker"`（契约的
0.25 m / 0.25 rad 到达判定就靠它），而 controller_server 里没这个名字 → 立刻 abort。
因为走的是"goal checker 查不到"这条分支，**既没有异常栈、也没有 ERROR 以外的线索**，
info 级别日志里只看到"收到 goal 后 1 ms 就 Aborting"，所以之前白查了两轮。

教训（已写进各 baseline YAML 的注释）：**每个 baseline YAML 都必须显式给出
`progress_checker_plugins` / `goal_checker_plugins` 与对应插件段**，四个控制器一致。

### K.1 公式与数据来源

T_s = max( T_min,s , 1.5 · max_j t̃(s,j) )      T_min = 60 s（mixed 75 s）

## L. Round 0 第一轮调参（2026-11-15）：找出并修掉"墙进不了静态图"的真 bug

### L.1 问题定位（先把"参数问题"和"实现 bug"分开）

工作集 75 run 的失败分布给出两条非常干净的线索：

- `dead_end` 的 13 次失败，`min_clearance` **全是 ≈0.000 m**（成功的那 2 次是 0.16 m）；
- `dynamic_pedestrian` / `mixed` 的失败是 **-0.30 ~ -0.02 m**（真撞行人）。

顺着第一条查下去，定位到 `robot_benchmark/scenes.py::build_occupancy` 的**两个实现 bug**：

| # | bug | 后果 |
|---|---|---|
| 1 | 迭代范围正好等于几何包围盒，且只用"格心是否落在几何内"判定 → 比一格薄的几何一个格心都落不进去 | 几何可能整块漏标 |
| 2 | 几何是 **path frame**、代价地图是 **map frame**，而 `world_pose` **可能带旋转**；原实现按未旋转包围盒迭代 | **`yaw != 0` 的种子静态图一格都标不出** |

影响面：`dead_end` 5 个种子里 4 个、`narrow_passage` 5 个里 4 个的静态图**没有墙**。
机器人拿着"没有墙的地图"直接穿墙——这才是 `dead_end` 只有 2/15 的真正原因，**不是控制器参数问题**。

修法：先把几何按 `world_pose` 变换到 map 系取包围盒（含旋转），迭代时外扩 2 格，
再用"格心反变换回 path 系"做精确判定。同时补两条回归测试
（`test_static_map_marks_walls`、`test_pedestrians_not_in_static_map`），
`pytest` → **40 passed**。

### L.2 三轮实测对比（工作集前 5 种子；③ 未跑完，样本量见括号）

| 场景 | ① 原状（静态图无墙） | ② 修墙后（padding 0.02） | ③ +局部静态层+TEB 隔障参数 |
|---|---|---|---|
| `dead_end` | DWA 1/5、MPPI 1/5、TEB 0/5 | DWA 4/4、MPPI 4/4、TEB 0/4 | DWA 1/2、MPPI 2/2、**TEB 2/2** |
| `narrow_passage` | DWA 3/5、MPPI 4/5、TEB 4/5 | DWA 2/4、MPPI 3/3、TEB 3/3 | DWA 1/4、MPPI 3/3、TEB 3/3 |

结论：
1. **修墙是决定性的**：`dead_end` 的 DWA/MPPI 从 1/5 → 4/4；

## M. 遗留 1 结案：`/map` 进不了代价地图（2026-11-15）

### M.1 排查过程（花了很久，结论是"别自己发地图"）

| 观察 | 说明 |
|---|---|
| 代价地图日志 `Can't update static costmap layer, no map received` 连续 100+ 条 | 地图没被接收 |
| 成功那轮：警告在启动 16 s 后停止；失败那轮：一直不停 | 偶发 |
| 1 Hz 重发 96 s 仍不到 | 不是"发得太早" |

| 活体实验：发一张 **40×40 的小地图** | 全局和局部 costmap 都打出了 `StaticLayer: Resizing ... to 40 X 40` → **说明能收到小地图** |

大样本 + 两个订阅者 + 与 voxel 层叠加）。不再较劲，改用 Nav2 官方通路。

### M.2 修法：`nav2_map_server` + PGM/YAML

1. `scenes.write_nav2_map()` 按契约实例写 `.pgm`（P5，0=占用/254=空闲）+ `.yaml`（origin/resolution）；

3. `nav2_baseline.launch.py` 见到 `map:=` 就起 `nav2_map_server/map_server`（纳入 lifecycle），
   由它发布 `/map`；`simulation.launch.py` 透传 `map` 参数；
4. driver 检测到 `/map` 已有外部发布者就让位（不再自己发），并在 `m2_diag.external_map_publisher` 记录。

**效果**：几何偏离率从 100% 降到 11%（说明静态图真的进了代价地图），
`dead_end run403` 这个此前必挂的实例一次通过。

## §Q 2026-11-16 行人动态障碍（补做 9-2 之后的一个漏洞）

**问题**：正式 300 run 的 65 次 `collision` 全部落在 `dynamic_pedestrian` / `mixed`，
且三个基线都"看着人撞上去"。根因不是判分，是三个基线都没有**轨迹预测**：行人横穿时刻
`t_meet` 是按机器人 0.6 m/s 直线走反解的，现测反应来不及。

**做法**（详见 `results/9-3行人动态障碍.md`）：把行人做成"静态地图里的动态障碍"——
`/map_updates`（`map_msgs/OccupancyGridUpdate`）把每个行人的**横穿走廊**（法向 0.74 m、
预测 4.0 s）注进代价地图的 `static_layer`，三个基线共用同一份信息。

**踩到的坑（按发现顺序）**：

1. `/map_updates` 的类型是 `map_msgs/OccupancyGridUpdate`，不是 `nav_msgs/OccupancyGrid`。
   类型不匹配时 DDS **静默不投递**，整套功能等于没做（三次 run 的成绩小数点后第 4 位一致）。
2. patch 不能用 `create_timer` 驱动：跟随阶段的 `spin_once` 节拍会把定时器饿死，
   补丁一直停在 `t=0`。改成从 `/odom` 回调按 ≥0.2 s 间隔触发。
3. 只标"行人在哪"不够，必须标"行人会扫过哪条走廊"，且走廊**法向半宽**要覆盖
   `底盘外接半径 + 行人半径`（0.343+0.30+0.10）。否则机器人会在横穿线前 0.06 m 停车，
   行人照直走过去穿体而过（探针 `/tmp/probe2.py` 抓到 `d=0.11 m`）。
4. 礼让会连续 4~5 s 没有可行轨迹，`failure_tolerance 0.5 s` 会把它记成失败；
   `progress_checker.movement_time_allowance 10 s` 同样会误杀多次礼让。
   分别放宽到 10 s / 30 s。
5. 这两项是 `controller_server` 级参数，四份 baseline YAML 里的重复段必须删掉，
   否则 `_merge_controllers()` 的一致性校验会直接抛 `RuntimeError`（launch 失败）。

**结果**（同种子前后对照，5 seed × 3 基线）：
`dynamic_pedestrian` 9/15 → **14/15**（碰撞 5 → 0），`mixed` 9/15 → **10/15**（碰撞 6 → 2），
合计 18/30 → **24/30**。静态三场景回归 25/27 → 25/27（无系统性回归）。
`T_s` 复核：`freeze_time_limits.py` 报 0 行改写（60/60/60/60/75 不变）。
以上是**新冻结版本**的成绩；`out/9-2_official` 的 300 run 属于旧冻结版本，
两者不可混用（见 `results/9-1参数定稿.md` §7）。
