## 2. 逐条答复 9-1 §10「待确认决定」

### 2.1 主对比运动学 = omni

**结论：成立。** 三基线在 omni 下全部跑通（DWA `max_vel_y=0.6`、MPPI `motion_model="Omni"`、
TEB `max_vel_y=0.6` 走 holonomic 优化分支）。diff 仍只做迁移冒烟，未进主实验。
**不需要你们额外动作，确认一句即可。**

### 2.2 任务平面合速度 0.6 m/s

**结论：已按"共享执行层"实现并冻结。** 链路：

```
controller_server ─/cmd_vel_raw─▶ flat_speed_limiter ─/cmd_vel_limited─▶
    safety_supervisor ─/cmd_vel─▶ 底盘（只订阅 /cmd_vel）
```

- 限速按**等比缩放**保证 `√(vx²+vy²) ≤ 0.6`、`|wz| ≤ 1.5`，另有加速度限幅 `1.0/1.0/2.0`；
- 实测证据：三条成功 run 的峰值平面速度分别 **0.600 / 0.598 / 0.600**，即执行层确实在起作用；
- 为什么不用各 YAML 的原生约束：MPPI 的 `vx_max`/`vy_max` 各 0.6 **不等于**合速度上限
  （合速度可到 0.85）；TEB 同样只有 `max_vel_x`/`max_vel_y` 分轴约束，**无原生平面约束**
  （这就是 §2 里"TEB 也需确认"那一项，现确认：没有，已由执行层兜住）。

### 2.3 TEB 可用性

**结论：可用，且用的是官方源码，不是社区 fork。**
`rst-tu-dortmund/teb_local_planner` branch **`humble-devel`**（v0.9.1）+ `costmap_converter` branch `ros2`。

## 5. 三处影响你们读数的实现口径（请务必知道）

### 5.1 时间基准

`run.json` 的 `time_to_goal_s`、`trajectory.npz` 的 `t`、`judge` 判超时用的时间，
**一律相对本 run 起点**（`/odom` 时间戳是仿真时钟绝对值，采集时可能已经到 100 s+）。
曾经用绝对值把实际 18.5 s 的到达判成 125.9 s 超时，已修正。

### 5.2 场景必须与清单一致（硬校验）

对齐仓里原有的 `assets/scenes/scenarios/*.usd` 是**旧版清单**生成的，障碍位置和
`docs/scenarios/instances.yaml` 不一致——机器人一路在躲"另一套场景"的障碍，裁判却按新清单
算间距，出现过"最小间距 1 m 却卡死"的怪现象。现在：

- 场景一律用 `robot_benchmark/scenes.py` 按 `instances.yaml` 现生成（文本 USD）；
- 采集器开跑前做**硬校验**：代价地图致命格偏离清单几何 >25% → 该 run 直接作废并报错；
- 实测三条成功 run 的偏离率均为 **0.0%**。

### 5.3 单栈不变量

采集器第一步检查 `/cmd_vel`、`/clock`、`/odom` 以及 `/compute_path_to_pose`、
`/follow_path` 两个 action **各恰好 1 个发布者/服务器**，不满足直接报错。
（曾经同时跑着 2 个限速节点 + 3 个 Isaac，多节点抢发 `/cmd_vel` 互相清零，机器人一动不动。）

### 5.4 需要你们签字的那一条：全局代价地图改用清单几何

**做法**：`global_costmap` 增加 `static_layer`，内容由 `instances.yaml` 在每次采集时发布到 `/map`；
**局部避障与碰撞判定仍然用实时 `/lidar/points` 与真值几何**，未做任何简化。

**理由**：Isaac 射线雷达每帧仅约 500 个点（`pointid_step=12`）、近场 2.63 m 盲区，
标出的障碍是**带孔洞的细弧**。SmacPlanner2D 会从孔洞里规划穿过去，DWB 到跟前找不到可行轨迹
就停住——实测反复停在 x≈4.5 / 6.1 / 7.96，跑不出可用成绩（这属于"传感器采样不足"，
不是控制器能力差异，会把三基线一起压成 0 成功率，两个真相都测不出来）。

**代价（请你们判断可接受性）**：全局规划不再考察"从稀疏点云建图"的能力，
只考察局部避障 + 跟踪。**四基线共享同一静态图，公平性不受影响**；但若你们认为
"全局地图未知/需自建"是本实验要考察的一部分，这条必须否掉，我们改回纯点云方案
（那样需要先解决雷达采样密度，否则三基线都会失败）。

## 8. 复现命令（可以直接贴给需要自己跑一遍的人）

```bash
# 0) 环境

# 2) 按清单生成场景（纯文本 USD，不需要 Kit）
python3 -c "import yaml;from pathlib import Path;from robot_benchmark.scenes import write_scene;from robot_benchmark.scenario_gen import find_instance,default_manifest_path as d;doc=yaml.safe_load(open(d(),encoding='utf-8'));i=find_instance(doc,'static_avoid',1);print(write_scene(i,doc['world_poses'][str(i['seed'])],Path('$NAV_WS/out/scenes/static_avoid_01.usda'),'$NAV_WS/assets/robot_a_chassis_agl_chs03_f01.usd'))"

# 3) 起栈（一次只能起一个！driver 会做单栈校验）
cd $NAV_WS
ros2 launch robot_bringup simulation.launch.py nav2:=dwa demo:=false rviz:=false \
    duration:=0 scene:=$NAV_WS/out/scenes/static_avoid_01.usda
#    TEB 需先： export LD_LIBRARY_PATH=$HOME/teb_prebuilt/opt/ros/humble/lib/x86_64-linux-gnu:$LD_LIBRARY_PATH
#              source ~/teb_build_ws/install/setup.bash
#    MPC 需先： source ~/mpc_build_ws/install/setup.bash

# 4) 采集（另一终端）
cd $NAV_WS/src/robot_benchmark
python3 -m robot_benchmark.runner --backend nav2 --baseline dwa \
    --scenario static_avoid --runs 1 --out out/9-2 --timeout 60
```
